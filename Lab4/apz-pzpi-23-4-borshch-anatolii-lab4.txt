2 ЗАВДАННЯ
     В цій лабораторній роботі необхідно показати як можна масштабувати бекенд системи для роботи із великим навантаженням. Для цього, можна на вибір:
- масштабувати сервер горизонтально — багато копій сервера виконують однакові функції для різних користувачів;
- масштабувати сервер вертикально — різні мікросервіси виконують різні функції і масштабуються окремо одне від одного.
З технічної точки зору, масштабування можна виконати так:
- деплой сервера на Kubernetes кластер, разом із окремим load balancer-ом та
базою даних. При цьому треба буде показати коректну роботу системи при
збільшенні чи зменшенні кількості подів сервера чи окремих мікросервісів;
- деплой в serverless середовище (AWS Lambda, Firebase Cloud Functions або
аналогічне). 
Треба показати що система може зменшувати кількість активних
інстансів до 0, збільшувати її зі збільшенням трафіку і все ще коректно функціонувати.
- ваш власний спосіб показати що система може масштабуватись.
     На найвищий бал на цю роботу необхідно провести навантажувальне тестування за допомогою Gatling, JMeter, Locust чи іншого подібного інструмента і показати як зі збільшенням кількості серверів зростає кількість запитів на секунду яку витримує система.
3 ОПИС ВИКОНАНОЇ РОБОТИ
   3.1 Опис роботи
   У роботі обрано стратегію горизонтального масштабування бекенд серверу. Підхід полягає в тому, що замість збільшення обчислювальних ресурсів одного сервера збільшується кількість ідентичних екземплярів застосунку, кожен з яких здатний самостійно обробляти вхідні запити. Усі ці екземпляри функціонують паралельно та виконують однакові функції для різних користувачів.
   Горизонтальне масштабування є більш практичним вибором для даної задачі з кількох причин. По-перше, воно дозволяє нарощувати потужність системи без простою, нові екземпляри запускаються і підключаються до балансувальника без зупинки вже працюючих. По-друге, у разі відмови одного екземпляра решта продовжують обслуговувати трафік, що підвищує загальну відмовостійкість. По-третє, Kubernetes як платформа оркестрації надає вбудовані механізми для автоматичного або ручного масштабування Deployment-ресурсів, що суттєво спрощує роботу з розгортанням системи.
   Вертикальне масштабування у формі виділення незалежних мікросервісів не застосовувалось як основна стратегія, оскільки поточна система реалізована у вигляді єдиного монолітного API-сервісу. Декомпозиція на мікросервіси потребувала б суттєвих архітектурних змін, що виходить за межі завдань даної роботи.
   Система розгорнута у локальному Kubernetes-кластері, створеному за допомогою інструменту kind (Kubernetes IN Docker). Кластер надає повноцінне середовище для оркестрації контейнерів без потреби у хмарній інфраструктурі.
   Kubernetes - це платформа оркестрації контейнерів, яка автоматизує розгортання, масштабування та керування контейнеризованими застосунками. Основною одиницею виконання в Kubernetes є Pod, мінімальний об'єкт, який містить один або декілька Docker-контейнерів, що розділяють спільну мережу та сховище. Pods не створюються вручну напряму для продуктивних систем, ними керує Deployment, який декларативно описує бажаний стан: який образ запускати, скільки реплік підтримувати та як оновлювати застосунок. Якщо Pod впав або був видалений, Deployment-контролер автоматично запустить новий, щоб підтримати задекларовану кількість реплік. Для того щоб клієнти могли звертатися до Pods незалежно від їх динамічних IP-адрес, використовується Service - це абстракція, яка надає стабільну точку входу та розподіляє трафік між усіма здоровими репліками.
   Kind - це інструмент для локального запуску повноцінного Kubernetes-кластера, де кожен вузол кластера працює як окремий Docker-контейнер на хост-машині. Він імітує реальну багатовузлову архітектуру Kubernetes без потреби у хмарній інфраструктурі. Kind підтримує всі стандартні Kubernetes-ресурси, такі як: Deployments, Services, PersistentVolumes, і дозволяє швидко створювати та видаляти кластери однією командою.
   Центральним компонентом системи є бекенд-застосунок CareLink.Api, розроблений на платформі .NET 8. Він розгортається у вигляді Kubernetes Deployment. Для розподілу вхідного трафіку між репліками використовується Kubernetes Service типу ClusterIP з доступом через port-forward. Service виконує роль стабільної мережевої точки входу: незалежно від кількості реплік та їх адрес клієнт завжди звертається до одного й того ж endpoint. Kubernetes автоматично розподіляє запити між доступними pod-ами за алгоритмом round-robin. База даних Microsoft SQL Server розгорнута як окремий Deployment у тому ж кластері, з виділеним PersistentVolumeClaim для збереження даних між перезапусками pod.
   Можливість горизонтального масштабування забезпечується сукупністю декількох технічних рішень. Kubernetes Service як балансувальник навантаження. Kubernetes Deployment є основним інструментом керування кількістю реплік команда kubectl scale дозволяє миттєво збільшити або зменшити кількість запущених екземплярів сервера.
   Для навантажувального тестування використовувався Apache Jmeter. Тестовий план описаний у файлі heavy-load-crud.jmx, який включає попередню автентифікацію тестового користувача для отримання токена доступу, після чого виконувалась серія повторюваних API-запитів під умовами високої конкуренції.
   Параметри навантажувального тестування були однаковими для кожного варіанту масштабування: 
• 120 паралельних потоків, що моделюють 120 одночасних користувачів; 
• період 20 секунд, протягом якого потоки поступово запускаються;
• 25 ітерацій на потік; таймаути підключення 10 секунд та очікування відповіді 60 секунд.
     Аналіз поведінки системи під навантаженням дозволяє визначити ресурси, які вичерпуються першими при нарощуванні трафіку. 
     Першим і основним вузьким місцем за умов горизонтального масштабування API є база даних. MSSQL розгорнутий як єдиний інстанс, і всі репліки API звертаються до нього одночасно. При зростанні кількості паралельних запитів збільшується час очікування SQL-запитів через конкуренцію за блокування, зростає навантаження на CPU та дискову підсистему БД, а пул з'єднань з базою може виявитися недостатнім.
     Другим обмеженням є CPU-ресурси pod API. При великій кількості одночасних запитів кожен pod може досягти насичення за CPU. цей ефект частково нівелюється горизонтальним масштабуванням, кожна нова репліка бере на себе частину навантаження.
     Третім обмеженням є мережева підсистема локального стенду. Kind-кластер функціонує всередині Docker на одній хост-машині, тому port-forwarding для доступу до Service вносить затримки, не характерні для хмарного розгортання.
