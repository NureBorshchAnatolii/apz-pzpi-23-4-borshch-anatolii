2 ЗАВДАННЯ

     На цій лабораторній роботі потрібно розробити мобільний програмний застосунок для будь-якої поширеної на сьогодні мобільної платформи. Мобільний застосунок повинен бути частиною системи і повинен взаємодіяти з нею. Для реалізації програмного застосунку можна використовувати технології для реалізації програмного забезпечення для мобільних платформ, вказані лектором, а саме Kotlin для Android та Swift для iOS. Звіт повинен містити опис прийнятих інженерних рішень. У ньому повинна бути показана будова мобільного застосунку та його взаємодія з іншими частинами системи.


3 ОПИС ВИКОНАНОЇ РОБОТИ
	3.1 Опис роботи

     Відповідно до умов завдання, для реалізації мобільного застосунку дозволено використовувати Kotlin (Android) та Swift (iOS). Однак після аналізу вимог проєкту було прийнято рішення розробити застосунок на платформі Flutter (Dart). 
Flutter обрано з таких причин:
• Кросплатформенність: один код покриває iOS та Android, що критично для MVP де важлива швидкість виходу на ринок.
• Dart синтаксично близький до Java (Kotlin)
• Flutter має вбудований HTTP клієнт та підтримку JWT-авторизації через заголовки - що повністю відповідає архітектурі створеної системи.
• Hot Reload значно прискорює цикл розробки UI.

   Застосунок побудований за принципом розподілу відповідальностей Separation of Concerns. Кодова база розділена на два основних шари:
• Core - Базові сервіси, конфігурація, тема, утиліти
• Screens - UI-екрани, згруповані за функціональними модулями

   Папка core/ містить інфраструктурний код, що використовується усіма екранами:
• ApiClient - HTTP-клієнт з підтримкою GET/POST/PUT/DELETE, JWT-авторизацією та обробкою помилок через ApiException
• AuthService - ChangeNotifier для зберігання JWT-токену та userId в SharedPreferences; забезпечує реактивний стан авторизації
• AppConfig - Конфігурація URL бекенду, підтримує localhost, 10.0.2.2 та LAN IP 
• AppTheme - Визначає стиль AppBar, Card, Input, Button.

   Папка screens/ містить 9 екранів, згрупованих за 7 функціональними модулями:
• auth/ - Вхід в систему, Реєстрація в системі
• home/ - Dashboard з коротким IoT-зведенням
• iot/ - Поточні показники, Історія
• notifications/ - Список сповіщень, Деталі
• chat/ - Список чатів, Переписка
• cognitive/ - Список вправ, Вправа, Результати
• profile/ - Перегляд, Редагування
• relatives/ - Список, Додати, Звіт
   Діаграма прецедентів (див. рис. ) відображає взаємодію трьох акторів системи з функціями застосунку:
• Літній користувач: авторизація, перегляд IoT-показників, сповіщення, повідомлення, когнітивні вправи, редагування профілю.
• Родич: авторизація, повідомлення, управління родичами, перегляд звітів та IoT-даних підопічного.

   Діаграма компонентів (див. рис. Б.4) показує чотири шари мобільного застосунку та їх взаємодію з бекендом:
• UI Layer - Auth, Dashboard, IoT, Messages, Exercises, Profile screens
• State Management - AuthBloc, IoTBloc, NotificationBloc, MessageBloc, ExerciseBloc, UserBloc
• Services - ApiService, AuthService, PushService
• Local Storage -SecureStorage, SharedPreferences

   Діаграма діяльності (див. рис. Б.1) описує основний сценарій використання застосунку з перегляду IoT даних.
